# Chapter 3: RISC-V ISA

## 3.1 Assembly Language Instructions

==Computer architecture is the **interface between hardware and software**, also known as the **Instruction Set Architecture (ISA)**.==

> ### 3.1.1 Design Goals for ISA
>
> - **Maximize performance** - Achieved through regularity (easy to pipeline, SIMD)
> - **Minimize cost** - Through simple ISA that's easy to build
> - **Reduce design time (time-to-market)** - Simple ISA is easy to design and test
> - **Minimize memory space** - Through compact encoding and fewer registers (embedded systems)
> - **Minimize power consumption** - Using SIMD, FMA, Vector extensions (mobile systems)
>
> **Key Principle:** The ISA should be **scalable, flexible, and extensible**.
>
> ### 3.1.2 CISC vs. RISC
>
> #### 1. Complex Instruction Set Computer (CISC) ==Software== 
>
> - **Implementation:** Complex instructions directly implemented by hardware
> - **Instruction Set:** Many instructions of variable size, optimized for memory size
> - **Registers:** Typically fewer registers (large micro-store size required)
> - **Examples:** Intel x86, IBM 360, DEC VAX; Dominant before the 1980s
>
> - **Cons:**
>   1. **Polynomial Evaluation** (VAX): Takes a variable, table of coefficients, and degree
>   2. **CALLS** (VAX): Handles stack alignment, argument pushing, entry mask, register saving, PC/FP/AP/condition codes/trap bits, and jump
>   3. **REP MOVSB** (x86): Copies memory until RCX == 0; can touch millions of bytes, execute for thousands of cycles, and be interrupted/resumed
>
> #### 2. Reduced Instruction Set Computer (RISC) ==Hardware==
>
> - **Implementation:** Simple instructions designed for efficient pipelining
> - **Instruction Set:** **Fixed-size instructions**, more registers
> - **Architecture:** "Load/Store" architecture - only load/store instructions access memory
> - **Examples:** RISC-V, MIPS, Sun SPARC, HP PA-RISC, IBM PowerPC, ARM
>
> - **RISC Era (Caching Available):**
>
>   - I-cache eliminates most instruction fetches from memory
>
>   - D-cache improves data access
>
>   - Simple, regular instructions enable efficient pipelining
>
>   - Mature compiler techniques replace assembly code
>
>   - Reduced core supports diverse applications (HPC, DB, Media, Mobile)
>
> ### 3. Modern Landscape (RISC)
>
> 1. **GPU sales dominate** the computing market
> 2. **Memory remains expensive and slow**
> 3. **AI applications** need matrix multiply accelerators or tensor operations
> 4. **AI models change rapidly** - compilers can't keep up; fast library functions are more practical
> 5. **All modern processors include complex instructions**
>
> ### 3.1.3 RISC Design Philosophy
>
> 1. **Simplicity Favors Regularity**
>
> - Fixed size instructions
> - Small number of instruction formats
> - Opcode always in the first several bits
>
> 2. **Smaller is Faster**
>
> - Limited instruction set / registers / addressing modes
>
> 3. **Make the Common Case Fast**
>
> - Arithmetic operands from registers (load/store machine)
> - Allow instructions to contain immediate operands
>
> 4. **Good Design Demands Good Compromises**
>
> - Balance between instruction format and number of operands supported
>
> ### 3.1.4 Compiler vs. Assembly Language
>
> **Important Note:** Instruction sets are measured by how well **compilers** use them, not by programmers.
>
> ### 3.1.5 The RISC-V (RV32/64/128)
>
> - **Status:** Relatively new, open standard, license/royalty-free ISA
> - **Timeline:**
>   - x86: 1978 (~48 years)
>   - ARM: 1985 (~41 years)
>   - RISC-V: 2010 (~16 years)
> - **Base Implementation:**
>   - **I**: Base Integer instructions
>   - **E**: Base for embedded systems (e.g., only 16 registers)
>
> - **Standard Extensions:**
>   - **M**: Multiply and Divide
>   - **A**: Atomic memory instructions
>   - **C**: Compressed extension with 16-bit instructions
>   - **F and D**: Single and Double precision floating point
>   - **V**: Vector extension
>
> - **Other Extensions**
>
> - Base Implementation (I or E) → Standard extensions → More Standard ext. → Non-standard ext.

### 3.2.2 RV32I Register State (Architecture State)

**Architecture state** is the set of all architecturally visible information that determines processor behavior at any instant.

#### 1. General Purpose Registers (GPR, 32 * 32b) 

**Why x0 is Always Zero (Besides Frequency):**

- **Clear**: not `XOR X10, X10, X10; SUB X9, X10, X8`, use `SUB X9, X0, X8`
- **Copy**: `ADD X1, X0, X2`
- **Compare-and-branch**: `BEQ X5, X0, Label`
- **Memory Hints** (e.g., cache prefetching, 测试内存是否可访问) `LW X0, 0(X1)`

#### 2. Program Counter (PC, 32b)

- **Purpose:** Tracks current instruction address

#### 3. Control and Status Registers (CSR)

- 特权级 / 异常 / 中断 / 性能计数

**User-Mode CSRs:**

- **cycle**: Clock cycles (read-only)
- **instret**: Instruction counts (read-only)

**Machine-Mode CSRs:**

- **hartid**: Hardware thread ID (read-only)
- **mepc, mcause**: Used for exception handling

**Custom CSRs:**

- **mtohost**: Output to host (write-only, custom extension) 把数据写给宿主机（常见于仿真器）

**Important:** Architecture states must be saved during context switches (e.g., process switches, interrupts) so programs can resume correctly.

==**Hart:**  a hardware thread, which is often a "core" in a multicore chip，是最小的“执行上下文单位”。==

- 一个 hart：有自己的一套 PC、GPR、CSR

- 多核 CPU：每个 core 可能有多个 hart（如 SMT）

#### 4. Examples

```asm
# Simple Load-Modify-Store: A = A + 1
LW X2, 0(X1)     // Load A
ADDI X2, X2, 1   // Increment by 1
SW X2, 0(X1)     // Store back
```

```asm
# Complex Expression: X = X*Y + Z (Without FMA)
LW F2, 0(X1)     // Load X
LW F3, 4(X1)     // Load Y
LW F4, 8(X1)     // Load Z
FMUL F2, F2, F3  // X*Y
FADD F2, F2, F4  // X*Y+Z
SW F2, 0(X1)     // Store result
```

```asm
# Complex Expression: X = X*Y + Z (With FMA)
LW F2, 0(X1)     // Load X
LW F3, 4(X1)     // Load Y
LW F4, 8(X1)     // Load Z
FMA F5, F2, F3, F4  // Fused: X*Y+Z
SW F5, 0(X1)     // Store result
```

![image-20260205014332726](assets\3.3.1.1.png)

| **R-type** | **funct7** | **RS2** | **RS1** | **funct3** | **RD** | **Opcode** | **Example**   |
| ---------- | ---------- | ------- | ------- | ---------- | ------ | ---------- | ------------- |
| ADD        | 0000000    | 00011   | 00010   | 000        | 00001  | 0110011    | Add  x1,x2,x3 |

- **Opcode**: defines the instruction class / major operation

    - funct7 = 0100000: `rs1 - rs2`
  - **funct3 = SRL (101)**
    - funct7 = 0000000: Logical shift right
    - funct7 = 0100000: Arithmetic shift right

### 3.3.3.1 Data Alignment

编译器维护一个映射表，对齐需求 = 数据大小（通常）：

| 类型   | 大小 | 对齐需求    |
| ------ | ---- | ----------- |
| char   | 1    | 1           |
| short  | 2    | 2           |
| int    | 4    | 4           |
| long   | 8    | 8（64 bit） |
| double | 8    | 8           |

#### Natural Alignment Principle

Data elements of a specific size should be stored at memory addresses that are **multiples of that size**:

- **SW/LW**: Addresses are multiples of 4 bytes
- **SD/LD**: Addresses are multiples of 8 bytes
- **SB/LB**: Always aligned (any address)

#### Benefits of Data Alignment

1. **Hardware Simplification:**

   - No cache line crossing (which would require multiple accesses)

   - No double TLB misses

   - No double page faults from single memory instruction

   - Better cache line utilization


2. **Avoiding Boundary Crossing**

   - **Memory Organization:**

     - Cache lines: typically 64 bytes (also 32 or 128 bytes)

     - Memory pages: 4KB, 16KB, or larger


   - **Naturally aligned data does not cross:**
     - Cache line boundaries / Memory page boundaries


   - **Crossing a boundary causes:**
     - Hardware complexity (two exceptions instead of one) / Performance degradation


   <img src="assets\3.3.3.3.png" alt="image-20260205020820543" style="zoom:50%;" />

#### Compiler Alignment Example

 `struct { int a; long long b; char c; double d };`

```bash
a: offset 0      (int, 4 bytes, aligned to 4)
b: offset 8      (long long, 8 bytes, aligned to 8) 
c: offset 16     (char, 1 byte)
d: offset 24     (double, 8 bytes, aligned to 8)
Total size: 32 bytes
```

#### Padding Rules

1. **Internal Padding:** Every member must start at an address that is a multiple of its own alignment requirement
2. **Trailing Padding:** The total must be a multiple of ==the largest alignment== requirement among its members

### 3.3.3.2 Stack and Frame Alignments

```asm
LW X2, -4(FP)     // Access local variable via frame pointer
SW X2, 8(X4)      // Access stack via base pointer
```

The base pointers (FP, SP, X4) must be properly aligned.

#### ABI Requirements

**Alignment determined by the Application Binary Interface (ABI):**

| ABI                                                 | Required Alignment |
| --------------------------------------------------- | ------------------ |
| Intel x86-64 System V / ARM Arch64 / MS Windows x64 | 16 bytes           |
| Older/embedded systems                              | 8 bytes            |

**RISC-V on Linux:** Uses `RISC-V ELF psABI` with **16-byte stack alignment**

#### C-Runtime (CRT) Enforcement

- **CRT ensures** proper stack alignment before calling main
- **CRT maintains** correct alignment at function entry
- This guarantees that offset-based access works correctly

### 3.3.3.3 Compiler Register Reordering

#### Reordering Rules

**Independent Variables (Reordering ALLOWED):**

```cpp
void function() { int a; char b; int c; }  // Can be reordered
```

**Struct Fields (Reordering FORBIDDEN):**
"Within a structure object, the non-bit-field members and the units in which bit-fields reside have addresses that increase in the order in which they are declared."

**Reasons for this constraint:**

1. **Binary compatibility** - Existing code depends on current layout
2. **Pointer arithmetic** - Standard guarantees pointer to struct points to first member
3. **Interoperability** - Must match external specifications

### 3.3.3.4 Instruction Operand Formats

#### 1. Zero and One Operand Instructions

**Stack Architecture:**

- All operations (jal, etc.) take operands from stack top
- These are 0-operand instructions
- Push and Pop are 1-operand instructions (memory ↔ stack)

### 2. Two Operand Instructions

**Format:** `A = A op B`

- One source operand must be identical to destination
- Typical of older architectures

### 3. Three Operand Instructions (RISC Standard)

**Format:** `A = B op C`

- Independent source and destination
- Standard in RISC-V R-type instructions
- Enables efficient code generation

### 4. Four Operand Instructions

**Format:** `A = B op C op D` (e.g., `A = B*C + D`)

- Most frequently used in matrix multiplication
- RISC-V F/D extension added fused-multiply-add (FMA) with R4-type (4 registers)

#### R4-Type Format for FMA

![image-20260205021647379](assets\3.3.3.4.png)

> ### RISC-V emphasizes **simplicity and regularity**, so why include four-operand instructions?
>
> This instruction is **extremely important** for the F/D (Floating Point) extension because:
>
> **Application to Linear Algebra:**
>
> - **Most common operation:** Matrix multiply
> - **Inner loop:** `C[i][j] = C[i][j] + A[i][k] * B[k][j]`
>
> **Performance Benefits:**
>
> - **Instruction count:** Substitutes two instructions (FMUL + FADD) with one
> - **Speed:** Faster execution by avoiding intermediate rounding
> - **Precision:** More precise result (only one final rounding, not two)
> - **Momentum:** Most newer machines include this instruction

> ### Question: Should We Have More Registers?
>
> ##### Arguments FOR More Registers
>
> - **Pipelined implementations** require more registers to avoid or minimize register dependencies
>
> - **Modern compilers** effectively allocate variables to registers, demanding more registers for optimal performance
>
> ##### Trade-offs AGAINST More Registers
>
> - **Increased overhead:**
>
>   - More saving/restoring during procedure calls and returns
>
>   - More context switch overhead
>
>   - Longer instruction format (more bits needed for operand designators)
>
>   - Longer register file access time
>
>
> - **Design principle:** Initially, registers were only for temporaries (small number sufficient, and smaller is faster). The evolution reflects changing compiler capabilities and hardware architecture.

>
> ##### 1️⃣ **C 语言代码**
>
> ```cpp
> int x = A[i];
> ```
>
> ##### 2️⃣ **编译器生成的汇编代码**
>
> ```asm
> slli t0, i, 2    # t0 = i * 4  (int)
> add t0, t0, base # t0 = &A[0] + i * 4
> lw x, 0(t0)      # load x, 0(t0)

> ##### Masked Operations
>
> - **Extract lower 10 bits of variable A** (or get remainder of A divided by 1024):
>   - `A and 1023` (i.e., `0000....1111111111`)
> - **Remove lower 10 bits of A**:
>   - `A and (1111.....1110000000000)`
> - **Set specific bits in a word** (e.g., 3rd and 4th bits):
>   - `OR ....0001100`

### 3.3.4 **Branch Instructions (SB)**

Example: `beq x1, x2, Label`

- Branches read two registers, compare them, and determine whether the branch should be taken or fall through
- Immediate is composed differently than S-type
- Used for control statements
- Function calls and jumps are handled with JAL (J-format)
- **Branch targets are encoded as PC-relative addressing** 
  - an offset relative to the current Program Counter


### 3.3.4.1 PC-Relative Addressing

- Use the immediate field as a 2's complement offset to PC
- Branch instructions change the PC by a small amount: either `PC+4` or `PC+offset`
- Can specify ±2¹¹ different addresses from the PC
- **Key difference**: In S-type (store instruction), the offset is relative to the base address; in SB-type (branch), the offset is relative to PC
- **Offset units differ**: ==For store instructions, offset is in bytes; for branch instructions, offset is in two bytes (half word)==
  - Why? RISC-V instructions are either 32-bit (regular) or 16-bit (compressed, C extension), so doubling the branch range using two bytes as a unit is more efficient.

### 3.3.4.2 Scaling Branch Offsets

- If all instructions are words (32-bit), the immediate value could be scaled by 4x before adding to PC, allowing one branch instruction to reach ±2¹¹ × 32-bit instructions either side of PC
  - `If branch taken: PC = PC + immediate * 4`
  - `If branch fall through: PC = PC + 4`
- Due to support for 16-bit instructions (required by C extension), the ISA only scales the immediate by 2 (2 bytes)
- **Result**: RISC-V branch instructions can only reach ==±2¹⁰ × 32-bit== instructions (±4KB)

### 3.3.5.1 Loading a 32-bit Constant into a Register

**Option 1**: Store in memory and use LW instruction (load instruction is usually expensive)

**Option 2**: Use LUI and ADDI instruction pair

```assembly
# 0x12345678
lui  x1, 0x12345          # move 20-bit value to upper 20 bits in x1
addi x1, x1, 0x678        # add lower 12 bits to x1
# x1: [0x12345][0x678] (20 bits | 12 bits)
```

#### Corner Case: When Lower 12 Bits > 0x800

```assembly
# 0x12345800
lui  x1, 0x12345
addi x1, x1, 0x800
```

Problem: The sign bit is on (0x800 = 100000000000 in binary), so the immediate is sign-extended to `FFFFF8000` in the 32-bit register. This is incorrect!

**Solution**: Use the pseudo-instruction `li x1, 0x12345800`, which the assembler handles by adjusting the upper immediate (e.g., making it `0x12346` instead of `0x12345`).

## 3.3.5.3 Memory Operands

- Simple variables can be allocated in registers
- Complex data structures (arrays, strings, structures) are stored in memory
- Use load instructions to move data from memory to registers, specifying the data address

**Example**: Access `A[8]` where A is a 32-bit integer array with starting address in x1

```asm
lw x2, 32(x1)     # Load word from memory
```

**Exercise 1**: 64-bit integer array, accessing `A[100]`

- **Answer**: `LD x2, 800(x1)` (8 bytes × 100 = 800 bytes)

**Exercise 2**: Struct with `{int green; int red; int blue}`, accessing `A[100].red`

- Struct size: 12 bytes
- Offset to `red` field: 4 bytes
- Total offset: `100 × 12 + 4 = 1204 bytes`
- **Answer**: `LW x2, 1204(x1)`

**Exercise 3**: Complex struct `{int white; long count; char c; int red; int blue}`, accessing `A[100].red`

- Struct layout with padding: `4, pad 4, 8, 1, pad 3, 4, 4` = 28 bytes
- Struct size must be multiple of largest field (8 bytes), so total: 32 bytes
- Offset to `red`: `4 + 8 + 1 + 3 + 4 = 20 bytes` (relative to struct start)
- Total offset: `100 × 32 + 20 = 3220 bytes`
- **Answer**: `LW x2, 3220(x1)`

### 3.3.5.4 Fallacy and Pitfall: The Register Window Problem

- Compilers can allocate **scalar variables** in registers, but ==NOT aggregate data structures like arrays, strings, or stacks==
- **Most memory loads/stores originate from array/string/stack references**, not scalar variables
- Therefore, having a large number of registers does not significantly help performance

## 3.3.6 Jump Instructions

`jal` 的标准动作是：

1. 计算跳转目标地址。
2. **将返回地址 ($PC + 4$) 写入 `rd`。**
3. 更新 $PC$ 到目标地址。

![image-20260205024617683](assets\3.3.6.png)

- Used for indirect jumps (computed at runtime)
- Typically used for return addresses and function pointers

> ## Why Jump and Link? Why Not Normal Jumps?
>
> RISC-V has only Jump and Link instructions (JAL, JALR), not separate jump and call instructions:
>
> - The `rd` field can be ignored if not needed (pseudo-instruction `J` sets `rd=0`)
> - Even if unused, the compiler can discover the link register is unused and reuse it for other purposes
> - This maintains **simplicity and regularity** of the ISA
> - Avoids needing multiple instruction formats
>
> **Trade-off**: Normal jumps don't need `rd`, so that field could be used for immediate, giving 32x greater jump range. But this requires another instruction format (25-bit immediate), which is not worth the complexity.

### 3.3.6.1 JALR Instruction Details

- JALR is an indirect branch in I-type format
- Usually used for addresses computed at runtime (return addresses, function pointers, etc.)
- 用于：函数返回 / 函数指针调用 / jump table（分支表）

```asm
rd ← pc + 4              // 保存返回地址（link）
pc ← (rs1 + imm) & ~0x1  // 跳转目标（清最低位）
						 // 指令地址 至少 2-byte 对齐，所以 PC 最低位必须是 0
						 // 即使 rs1 里最低位被拿来“塞标志位”，也不会出错
```

`JALR` 的三种用途：

```asm
jalr x0, rs1, imm    // 1️⃣ 普通间接跳转
jalr x1, rs1, imm    // 2️⃣ 函数调用（call）
jalr x0, x1, 0      // pc ← ra, 3️⃣ 函数返回（return）
```

> ## Return Address Stack and Return Prediction
>
> - Hardware uses a **return address stack** for branch prediction
> - A call pushes return address on stack; return pops from stack
> - Hardware infers return instruction using calling convention: if JALR uses x1/ra with offset 0, assume it's a return
> - This prediction can be wrong if compiler stores branch table in x1

> ## Why No BLE and BGT Instructions?
>
> RISC-V has BLT and BGE, but not BLE or BGT. This maintains regularity:
>
> - **To implement BGT**: Simply swap operands of BLT: `BGT x2, x1, label` becomes `BLT x1, x2, label`
> - **To implement BLE**: Simply swap operands of BGE: `BLE x2, x1, label` becomes `BGE x1, x2, label`
>
> **Design benefit**: Checking bounds efficiently
>
> - Range check `0 ≤ x < y` normally requires 2 instructions with signed comparison
> - With unsigned comparison: `BGEU x, y` (branch if x ≥ y to handle out-of-bounds) is more efficient

## 3.4 Assembly Code vs. Binary

- Too tedious to write programs in binary
- Assemblers provide:
  - **Mnemonics** for instructions: `add x1, x2, x3`
  - **Pseudo-instructions**:
    - `mov x1, x2` → `add x1, x2, x0`
    - `J label` → `jal r0, label`
    - `li x1, 6175` → `lui x1, 2; addi x1, x1, -2017` (exact sequence depends on immediate)
  - **Symbols** for locations and data:
    - `bnz x1, loop_begin`
    - `lw x1, flag`
    - `J label`

### 3.4.1 GCD Example in C

```c
// require: a >= 0 && b > 0
int gcd(int a, int b) {
  int t;
  while(a != 0) {
    if(a >= b) {
      a = a - b;
    } else {
      t = a;
      a = b;
      b = t;
    }
  }
  return b;
}
```

### 3.4.2 GCD in RISC-V Assembly (Without ABI)

~~~assembly
// a: x1, b: x2, t: x3
begin:
    beq x1, x0, done        // if(x1 == 0) goto done
    blt x1, x2, b_bigger    // if(x1 < x2) goto b_bigger
    sub x1, x1, x2          // x1 := x1 - x2
    j begin                 // jump back to begin
b_bigger:
    add x3, x1, x0          // x3 := x1 (copy x1 to x3)
    add x1, x2, x0          // x1 := x2
    add x2, x3, x0          // x2 := x3
    j begin                 // jump back to begin
done:                       // now x2 contains the gcd

// Alternative swap without x3:
x1 = x1 xor x2
x2 = x1 xor x2
x1 = x1 xor x2
~~~

**Note**: If a and b are pointers (`*a`, `*b`), compiler won't allocate them to registers because they might point to the same memory location.

## 3.5 Application Binary Interface (ABI)

Calling convention defines rules for:

- **Register usage** in passing arguments and results for function calls
- **Callee-saved vs. Caller-saved registers**

#### Register Aliases

| Purpose            | Physical Registers | ABI Names | Type         |
| ------------------ | ------------------ | --------- | ------------ |
| Zero               | x0                 | zero      | -            |
| Return Address     | x1                 | ra        | Caller-saved |
| Stack Pointer      | x2                 | sp        | Callee-saved |
| Global Pointer     | x3                 | gp        | Callee-saved |
| Thread Pointer     | x4                 | tp        | Callee-saved |
| Temporary          | x5-x7, x28-x31     | t0-t6     | Caller-saved |
| Saved Registers    | x8-x9, x18-x27     | s0-s11    | Callee-saved |
| Function Arguments | x10-x17            | a0-a7     | Caller-saved |

**Convention**:

- a0-a7: Function argument registers (first 8 arguments)
- a0, a1: Function return value registers
- ra (x1): Return address
- sp (x2): Stack pointer

### 3.5.1 Calling GCD Using ABI

Assume computing GCD of s0 and s1, result in s2:

```assembly
// Prepare arguments in a0, a1
mv a0, s0
mv a1, s1

// Save caller-saved registers on stack
addi sp, sp, -8         // allocate stack space
sw t0, 4(sp)
sw t1, 0(sp)

// Call function
jal gcd

// Restore caller-saved registers
lw t0, 4(sp)
lw t1, 0(sp)
addi sp, sp, 8          // pop stack space

// Get result and store
mv s2, a0
```

### 3.5.2 GCD Function in RISC-V Assembly (Using ABI)

```assembly
// a: a0, b: a1, t: t0
gcd:
    beqz a0, done           // if(a0 == 0) goto done
    blt a0, a1, b_bigger    // if(a0 < a1) goto b_bigger
    sub a0, a0, a1          // a0 := a0 - a1
    j gcd                   // recursive call (tail call)
b_bigger:
    mv t0, a0               // t0 := a0 (temporary)
    mv a0, a1               // a0 := a1
    mv a1, t0               // a1 := t0
    j gcd                   // jump back
done:
    mv a0, a1               // move result to a0 (ABI requirement)
    ret                     // jr ra (return to caller)
```

**Key points**:

- Result must be returned in a0 (ABI requirement)
- Arguments passed in a0, a1
- Temporary register t0 used for swapping

> ## Multiply Instruction
>
> - `mul x1, x2, x3`: multiply operation in 'M' extension (`x1 := x2 * x3`)
> - If 'M' extension NOT implemented, this is an **illegal instruction**
>
> **Handling missing extensions**:
>
> - Code compiled for RV32IM running on RV32I machine: mul causes illegal instruction exception
> - Exception handler can abort the program or **emulate** the instruction in software
>
> ```asm
> mul_emulate:
>     mv t0, x2         # t0 = a
>     mv t1, x3         # t1 = b
>     mv t2, x0         # t2 = result, initial value 0
>     li t3, 32         # 32-bit loop
> 
> mul_loop:
>     andi t4, t1, 1    # Check if the least significant bit of b is 1
>     beqz t4, no_add   # If it is not 1, no need to add
> 
>     add t2, t2, t0    # Add a to result
> 
> no_add:
>     slli t0, t0, 1    # Shift a left by 1 (multiply by 2)
>     srai t1, t1, 1    # Shift b right by 1 (divide by 2)
>     subi t3, t3, 1    # Decrement loop counter
>     bnez t3, mul_loop # Continue if not finished
> 
>     mv x1, t2         # Store result in x1
>     ret
> ```
>

## 3.6 Exception Handling

When an exception occurs:

**Hardware actions**:

1. Save exception information in CSRs:
   - `mepc` – exception program counter
   - `mcause` – cause of exception
   - `mstatus.mpp` – privilege mode
2. Jump to trap handler address (stored in `mtvec` CSR)
3. Increase privilege level

**Software handler** then:

1. Takes over and performs necessary actions
2. Determines whether to abort program or handle the exception
3. Returns control to program or handles error

### 3.6.1 Software for Interrupt Handling

Common handler (CH) flow:

1. **Save all GPRs** into memory pointed by `mscratch`
2. **Pass context** (`mcause`, `mepc`, stack pointer) to interrupt handler (IH) function
3. **Determine return instruction** - modify `mepc` (+4 or +2 based on instruction size)
4. **Load all GPRs** from memory
5. **Execute ERET**, which:
   - Sets `pc ← mepc`
   - Pops `mstatus` (mode, enable) stack

### 3.6.2 Common Interrupt Handler Assembly 

```assembly
common_handler:
    # Swap sp and mscratch
    csrrw sp, mscratch, sp
    
    # Save all registers to stack (x2/sp saved later)
    addi sp, sp, -128
    sw x1, 4(sp)
    sw x3, 12(sp)
    ...
    sw x31, 124(sp)
    
    # Save original sp (now in mscratch)
    csrr s0, mscratch
    sw s0, 8(sp)
    
    # Continue to call interrupt handler function...
```

```c
long illegal_inst_ih(long cause, long epc, long *regs)
{
    // Fetch instruction

    // Check opcode & function codes
```

## 3.7 Instruction Set Design Issues

Key questions to consider (revisited after datapath implementation):

- Should ISA have 1024 general-purpose registers?
  - 影响寄存器访问速度和上下文切换的成本。更多寄存器能减少内存访问，但会增加硬件复杂度。

- Compare-and-Branch vs. Condition-Code-based branches?
  - 比较和分支（Compare-and-Branch）：通过显式比较寄存器值进行跳转，灵活性强。
  - 条件码分支：条件码用于决定跳转，硬件实现简单但灵活性差。

- Support fast procedure calls with single instruction?
  - 减少过程调用的开销，提升性能，但增加指令集复杂度。

- Support 3-operand or 4-operand formats?
  - 3 操作数格式：减少指令长度，简化指令集。
  - 4 操作数格式：增加灵活性，可以减少寄存器交换次数，但指令复杂度增

- Use register pairs for wider data?
  - 寄存器对可支持更宽的数据处理，减少内存访问，但会增加硬件复杂度。

- Support post-increment memory loads?
  - 寄存器对可支持更宽的数据处理，减少内存访问，但会增加硬件复杂度。

- Dedicated bit for static branch prediction?
  - 专用位简化分支预测，提升性能，但增加指令集的复杂性。

- Many other design trade-offs...
  - 专用位简化分支预测，提升性能，但增加指令集的复杂性。
